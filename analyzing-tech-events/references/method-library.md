# 方法库（Method Library）

本文件是 SKILL.md 各阶段引用的分析工具详细操作手册。章节号与 SKILL.md 中的引用一一对应。

---

## §1 信源分级与循环印证

### 优先级（从高到低）

| 信息类型 | 一手来源 |
|---------|---------|
| 产品更新/技术决策 | 官方博客、GitHub Release Notes、README/文档、创始人公开发言 |
| 项目健康度 | commit 历史、issue 响应速度、PR 合并记录、贡献者结构 |
| 融资/商业数据 | 官方公告、工商/监管文件、投资机构官方宣布 |
| 用户口碑 | GitHub Issues/Discussions、HN、Reddit、V2EX、知乎、X/Twitter 技术圈讨论 |
| 行业分析 | 权威媒体**原创**报道（署名、有独立采访） |
| 学术/技术原理 | arXiv 论文（`https://export.arxiv.org/api/query?search_query=...`）、会议论文集、官方技术报告 |

### 循环印证（circular reporting）

多家媒体转述同一篇原始稿子，信息量等于一篇。识别方法：追每条关键事实到**最早的原始出处**；追不到原始出处的"事实"标记为「出处不明」。

### 诚实标注

- 搜不到的信息写「暂缺」+ 已尝试的搜索路径
- 无法确认真伪的争议信息写「存在争议，正反信源如下」
- 禁止用想象填充任何空缺

## §2 炒作信号清单（信噪比体检）

逐项核对，每项命中记 1 分：

| # | 信号 | 核对方法 |
|---|------|---------|
| 1 | star 增速与 issue 活跃度背离 | star 暴涨但 Discussions/Issues 区几无真实使用反馈 |
| 2 | demo 视频剪辑痕迹 | 只展示成功案例、加速播放、不展示失败与重试 |
| 3 | 「改变一切/终结者/吊打X」措辞密度 | README 与传播文案中夸张措辞占比 |
| 4 | 无第三方复现 | 发布 72 小时内无可信的无利益关联复现报告 |
| 5 | 依赖特定 prompt/环境才能复现演示效果 | 社区复现尝试普遍失败或效果显著缩水 |
| 6 | 团队匿名或信息模糊 | 查不到团队背景、过往项目、可验证身份 |
| 7 | 账号/营销路径异常 | 发布时间点踩热点、批量马甲发帖、买转发 |
| 8 | 许可证或条款暗示 | license 突然更换、CLA 条款、商用限制、数据回传条款 |

**定级**：0–1 分＝高信噪比；2–4 分＝中；5 分以上＝低（接近纯营销事件，全部结论按 D 级推测对待）。

## §3 释放方动机清单

对每个动机，记录「支持证据 / 反对证据 / 可观察的验证信号」三栏：

| 动机 | 典型特征 | 验证信号 |
|------|---------|---------|
| 抢标准/生态位 | 生态位是入口级、协议宽松（MIT/Apache）、快速推 SDK 和集成 | 短期内密集推出开发者工具、联盟、兼容性认证 |
| 众包工程 | 维护成本高的基础设施类项目、issue 区活跃、官方快速响应 PR | 官方对社区贡献的整合速度 |
| 商业化漏斗 | 开源社区版 + 托管/企业版双轨、开源版功能受限或部署受限 | 定价页、云服务、SLA 条款 |
| 商品化互补品 | 释放方的主营业务被该品类的闭源玩家压制，开源意在压低对方利润池 | 释放方主营产品与该品类的关系（互补则开源，替代则慎） |
| 人才与声誉 | 团队署名清晰、博客深挖技术细节、招聘页同步更新 | 发布后招聘信息的关联变化 |
| 数据获取 | 项目申请异常宽的权限、回传遥测、条款要求数据共享 | 隐私政策、遥测开关、权限申请清单 |

组合动机是常态（通常 2–3 条并存），单一动机结论要有「为什么排除了组合」的说明。

## §4 ACH 矩阵（竞争性假设分析）操作步骤

1. **列假设**：从 §3 选出 2–4 个 + 1 个「其他」（防止清单盲区）；
2. **列证据**：把 P1–P2 收集到的所有关键证据逐条列出（每条注明信源等级）；
3. **画矩阵**：行为证据、列为假设，每格填 `C`（一致）/ `I`（矛盾）/ `—`（无关）；
4. **诊断**：**关注 I 最少的假设，而不是 C 最多的假设**（证据都容易编，矛盾才致命）；
5. **淘汰与存留**：被多条高等级证据矛盾的假设淘汰，写明淘汰理由；存留假设按矛盾数排序给出置信度（高/中/低）；
6. **诚实列出无法区分的假设**：现有证据不足以区分时，明说「需要什么证据才能区分」，并把它转化为可观察信号。

**格式示例**：

```
证据＼假设        | A 创业预热 | B 大厂卡位 | C 理想主义 | D 其他
匿名发布          |     C      |     I      |     I      |   —
无商业化条款      |     I      |     C      |     C      |   —
发布即配合播客造势 |     C      |     C      |     I      |   —
→ 结论：A 存留（0 矛盾，置信度中高）；B、C 淘汰（理由…）
→ 无法区分 A 与 D，区分信号：未来 30 天是否出现融资公告
```

## §5 Why Now 分析法

四条线找交点，每条线给出「三年前的状态 / 现在的状态 / 触发变化的具体事件」：

| 线 | 问的问题 |
|----|---------|
| 成本线 | 推理/训练/算力成本是否刚跨过阈值？ |
| 能力线 | 依赖的底层模型/组件是否刚出现突破？ |
| 使能线 | 依赖的协议/框架/基础设施（长上下文、工具调用标准、沙箱）是否刚成熟？ |
| 需求线 | 下游需求/预算/政策是否刚打开窗口？ |

**判断规则**：四条线中至少两条在近期（≤ 6 个月）发生阶跃变化，事件才可能是技术节点；否则更可能是**营销节点**——这个判断本身要写进报告。

## §6 第一性原理组件化

把对象还原为组件，逐项判断「新原语」还是「已有组件的新编排」：

**Agent 类项目通用拆解模板**：

| 组件 | 判断要点 |
|------|---------|
| 规划（planning） | 任务分解是模型原生能力还是外置状态机/prompt 框架？ |
| 工具调用 | 工具集是新的还是标准集合？调用协议有无新原语？ |
| 记忆 | 跨会话记忆/向量检索/结构化状态，用的是什么方案？ |
| 多智能体编排 | 编排拓扑是新的还是既有框架（如某编排库）的配置？ |
| 沙箱执行 | 执行环境隔离方案？安全边界？ |
| 底层模型依赖 | 依赖哪家模型？换模型会塌吗？ |
| 数据回流 | 有无独占数据闭环（这是可持续壁垒，编排不是） |

**判断标准**：新原语（新的模型能力、新的交互协议、新的训练方法）→ 重大；新编排（已有组件的工程组合，无论 demo 多惊艳）→ 中等，且可被复制，护城河在于数据、分发、可靠性工程。

## §7 利益相关方地图与二阶传导链

### 地图模板（按事件增删）

| 相关方 | 升值/贬值 | 具体损益 |
|--------|----------|---------|
| 释放方 | ? | 短期得到什么，赌的是什么 |
| 闭源同类巨头 | ? | 护城河是否被腐蚀，应对选项 |
| 中间层（做同类能力的 SaaS/工具商） | ? | 最常见的受损方：能力被开源商品化 |
| 云厂商/算力方 | ? | 开源通常利好推理算力需求 |
| 开发者 | ? | 门槛变化、技能重估 |
| 最终用户 | ? | 价格、可选项、锁定风险 |

### 二阶传导链写法

格式：**一阶变化 → 二阶反应 → 三阶要素重估**，每环必须落到「谁的什么指标会怎么变」。

- 合格示例：「门槛降低（一阶）→ 纯『能做 agent』的开发者溢价消失，竞争焦点转向可靠性与数据回流（二阶）→ 评测体系与沙箱算力涨价，垂直场景数据成为并购标的（三阶）」
- 不合格示例：「这将极大推动行业发展」（无主体、无指标、无方向，禁止出现）

### 「谁受损」优先

受损方的护城河腐蚀点和可能的应对（降价/捆绑/诉讼/加速自研）往往是后续事件的剧本，写出「最可能的应对」。

## §8 系统动力学常见回路

用于判断事件后的生态演化方向，引用时说明「这是一个哪类回路、杠杆点在哪」：

| 回路类型 | 模式 | 事件分析的用途 |
|---------|------|---------------|
| 成功致败（limits to growth） | 增长→负担→质量下降→增长受制 | 开源项目 star 暴涨后维护崩溃、分叉 |
| 飞轮（reinforcing） | 用户→数据→体验→用户 | 判断谁有数据回流，谁只会被掠过 |
| 公地悲剧 | 共享资源被过度使用 | 社区维护、免费 API、开放数据集的可持续性 |
| 时滞错觉 | 力量与结果之间有延迟 | 「发布即巅峰」类项目，热度与能力脱钩 |

杠杆点提示：改变信息流（评测、透明度）通常比改变规则更有效。

## §9 2×2 场景规划操作

1. 头脑风暴列出所有关键不确定性；
2. 按「影响大小 × 相互独立性」选出**两个**：影响最大且彼此独立（相关性高的合并成一个）；
3. 每个不确定性取两个对立取值，构造四象限；
4. 每个情景：命名（有画面感的短句）、概率（四者合计 100%，禁止都是 25% 的偷懒）、**触发信号**（可观察的领先指标，如「融资公告」「官方商业化页面上线」「核心维护者离职」）；
5. 概率校准：对照 §11 的基准比率，禁止无依据的 90%+。

## §10 可证伪预测写法

**四要素缺一不可**：

```
时间窗：明确截止时间（如「6 个月内」「2026-Q2 前」）
观察指标：可公开观察的信号（commit 数、公告、价格、第三方评测）
阈  值：多少算触发（「月 commit < 50」「出现收费页」）
证伪条件：什么情况出现则本判断作废（并且承诺届时公开修正）
```

**检验**：把预测读给一个不知道内情的人，问「三个月后怎么 objectively 判断对错」。答不出 → 重写。

数量：2–3 条。覆盖不同时间窗（一条 1–3 个月的短判 + 一条 6–12 个月的长判最佳）。

## §11 历史类比与基准比率

1. 找 2–3 个**结构相似**的历史事件（同为开源、同品类、同为无名团队/巨头释放）；
2. 每个案例记录：当时宣传 vs 12 个月后的实际结局；
3. 得出基准比率：类似事件中，「宣传效果在 12 个月内兑现」的比例；
4. 本事件按基准比率给初始概率，再用本事件特有证据向上/向下修正；
5. **写出类比失效点**（必备）：本次与历史案例的关键不同及其含义。没有失效点说明的类比是修辞，不是分析。
